# Combined 1x1/3x3 Packed-Object DMA

This repository contains a hierarchical, CPU-programmed DMA for loading packed
1x1/3x3 activation tiles and packed weight slices from DRAM into an 8-bank NPU
memory system. The CPU selects the operation through AXI4-Lite and supplies a
pointer to the exact packed object. The DMA generates row or weight-slice
descriptors, issues 32-bit AXI4 read bursts, inserts the required 3x3 boundary
zeros locally, and steers each returned word into four 8-bit SRAM banks.

The isolated DMA implementation successfully placed and routed on the FABulous
fabric at **736/800 `FABULOUS_LC` (92%)**. The full integrated simulation ran a
complete 3x3 workload followed by a complete 1x1 workload on the same live
DMA/NPU/SRAM instance and matched all **32,768** golden output values.

## Repository layout

All paths in this document are relative to the repository root.

### DMA RTL

The DMA source files are located in:

```text
user_design/combined_1x1_3x3_dma/
```

| File | Purpose and connections |
| --- | --- |
| `dma_a.v` | Top-level DMA integration shell. Instantiates `dma_axil_control`, `combined_hwc_channel_dma_agu`, and `dma_fetch_engine`; exposes the CPU AXI4-Lite slave, read-only DRAM AXI4 master, map stream, and debug/status word. |
| `dma_axil_control.v` | Implements the AXI4-Lite register interface, independent AW/W capture, pointer/configuration registers, request validation, readback, and sticky done/error status. Sends the accepted configuration and a one-cycle start pulse to the AGU. |
| `combined_hwc_channel_dma_agu.sv` | Address-generation unit. Converts one CPU request into activation-row or weight-slice descriptors and generates the 1x1/3x3 destination schedule, including local 3x3 boundary-padding descriptors. Its descriptor stream is consumed by `dma_fetch_engine`. |
| `dma_fetch_engine.v` | Executes AGU descriptors. Owns the AXI read FSM, address and beat counters, padding phases, backpressure, and AXI error checks. Instantiates `dma_axi_burst_planner` and `dma_map_datapath`. |
| `dma_axi_burst_planner.v` | Combinational child of `dma_fetch_engine`. Selects the next legal AXI burst length and clips a request at a 4-KiB boundary. |
| `dma_map_datapath.v` | Combinational child of `dma_fetch_engine`. Formats fetched or zero-filled words into the map stream, calculates destination SRAM addresses, selects the low/high four-bank mask, and detects descriptor completion. |
| `dma_npu_sram_adapter.sv` | Connects the DMA map stream to `npu_sram_wrapper`. It arbitrates activation SRAM addresses, writes four activation banks per 32-bit beat, and buffers the low 32-bit half of a weight group so the current NPU loader can shift eight weights together. |
| `combined_dma_npu_sram_top.sv` | Synthesizable integration of `dma_a`, `dma_npu_sram_adapter`, and `npu_sram_wrapper`. It connects the read DMA to the activation and weight-loading ports while leaving PSUM control on the NPU/controller path. |
| `top_wrapper.v` | Reference FABulous wrapper for isolated DMA synthesis and place-and-route. The FABulous flow uses the framework-managed `user_design/top_wrapper.v`; keep that file synchronized with this reference copy and do not also list it as a `compile_design` source. |

The normal FPGA build sets `MAP_SOURCE_METADATA=0`. This preserves the
functional map stream while tying monitor-only source-address metadata low, so
its duplicate address registers and per-beat metadata adder are not synthesized.
The testbenches enable this metadata only so their scoreboards can check every
source address and stride.

## How the DMA works

The current DRAM interface is a read-only, 32-bit AXI4 master. Software first
writes the operation configuration to AXI4-Lite address `0x08`, then writes the
packed-object pointer to `0x00`; the pointer write starts the DMA.

- A 1x1 activation object contains `16 x 16 x 8 = 2048` packed bytes. Each row
  is fetched as 32 AXI beats.
- A 3x3 activation object contains the valid `17 x 17 x 8 = 2312` bytes for an
  18x18 logical window. The DMA fetches 34 beats per valid row and generates one
  zero row and one zero column locally.
- A weight object contains one packed `8 x 8 = 64` byte slice and is fetched as
  one 16-beat request. The required 64-byte alignment prevents this slice from
  crossing a 4-KiB boundary.

For activation data, the first 32-bit beat of a group writes banks 0-3 and the
second writes banks 4-7 at the same SRAM address. `map_ready` reflects SRAM-port
ownership and directly backpressures AXI `RREADY`; data is not retired while the
array owns the relevant SRAM ports. Weight data uses one 32-bit holding register
because the existing NPU weight loader accepts eight 8-bit lanes simultaneously.

## Verification

Run the following commands from the repository root:

```bash
make -f Test/combined_1x1_3x3_dma/Makefile.dma_combined clean
make -f Test/combined_1x1_3x3_dma/Makefile.dma_combined model
make -f Test/combined_1x1_3x3_dma/Makefile.dma_combined unit
make -f Test/combined_1x1_3x3_dma/Makefile.dma_combined integrated
```

The verification uses three complementary mechanisms:

| Check | Mechanism and verified result |
| --- | --- |
| Python reference model | Independently reproduces all packed schedules and AXI plans. It passed 16 activation configurations and 40 weight configurations: 312 descriptors, 4,960 map groups, 304 bursts, and 9,360 DRAM beats. |
| Standalone RTL testbench | Uses a checked AXI DRAM model and scoreboards for map data, addresses, masks, padding, responses, ownership, and swaps. It passed 63 operations, 6,144 map commands, 374 bursts, and 11,588 read beats, including a 4-KiB row split and rejected writes while busy. |
| Integrated sequential testbench | Loads packed image/weight views through the real DMA AXI master, runs the shared NPU/SRAM hierarchy, drains PSUM results, and compares every output against golden `.mem` files. It passed a complete 3x3 layer followed by a live AXI-Lite mode change and complete 1x1 layer with one reset total. All 32,768 outputs matched; 688 bursts and 20,000 AXI beats were checked. |

The integrated regression validates the hardware mode transition, but its 1x1
input vector is independent of the preceding 3x3 result. It does not model a
writeback-and-reload dependency between the two layers.

## Not implemented

1. **First-layer raw HWC tensor input.** The current DMA expects software-packed
   eight-channel activation objects. It cannot directly select channels 0-7 or
   8-15 from an immutable `image[y][x][0...15]` first-layer tensor.
2. **General tile-boundary handling.** The current 3x3 schedule assumes a 32x32
   input divided into four 16x16 output tiles. Every tile therefore touches a
   vertical and horizontal image boundary, so every 18x18 logical window has
   exactly one locally generated zero row and one zero column. Larger images
   can contain interior tiles with no boundary padding, which the one-bit
   `tile_x`/`tile_y` schedule cannot currently express.
3. **DRAM writeback.** The DMA exposes only AXI read-address and read-data master
   channels. It does not drain completed output/PSUM SRAM banks, requantize
   results, pack later-layer activation objects, or issue AXI AW/W/B transfers.

## Findings

1. **AXI control is area-intensive.** The two largest local blocks are
   `dma_axil_control` (363 mapped cells) and `dma_fetch_engine` (328 before its
   children). The AXI endpoint BELs are hard resources, but the surrounding soft
   logic for independent channel capture, responses, sticky status, burst
   tracking, 4-KiB clipping, backpressure, and error checking consumes a large
   share of the LUT/FF budget.
2. **Use `--synth-extra-args=-noflatten` for module-level accounting.** This
   preserves hierarchy long enough for Yosys to print useful per-module local
   statistics. It should be a separate analysis build; normal PnR should use the
   flattened JSON.
3. **Consider a four-weight NPU load interface.** One AXI beat already carries
   four 8-bit weights. If the NPU weight loader could shift four lanes per event,
   `dma_npu_sram_adapter` could forward each beat directly and remove its 32-bit
   low-half buffer. This may reduce soft-logic storage and control.
